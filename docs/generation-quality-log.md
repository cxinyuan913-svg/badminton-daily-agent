# AI 生成內容查證紀錄（問題與解法）

這份記錄 badminton-daily-agent 在「AI 寫的東西是錯的、空的、或不像人寫的」這類問題上，遇過什麼、怎麼發現、根因是什麼、怎麼修、怎麼驗證。
用途：(1) 之後同類問題先查這裡；(2) 面試被問「遇過什麼困難」時的素材。
維護：每次 Raymond 審稿抓到新問題，claude.ai 新增一筆案例；本機 CLI 修好後補上 commit 與驗證結果。審稿準則本身在 `docs/video/review-guidelines.md`（R1–R12），這裡是「為什麼會有那些準則」的歷史。

---

## 一、整體架構：五道防線（2026-09-30 到 10-02 逐步長出來的）

| 防線 | 擋什麼 | 怎麼做 |
|---|---|---|
| 1. 資料層只給可驗證的事實 | 捏造、自己算錯 | 程式先從資料庫算出「事實清單」（facts）與故事候選，交給 LLM 的是整理好的事實，不是原始資料；必然成立的廢話（例：四強輸給冠亞軍）在這層就不產生 |
| 2. 提示詞＋審稿準則 | 敘事品質、用語 | `review-guidelines.md` 是唯一來源，每次產生都讀最新版；每條準則附 Raymond 抓到的反例 |
| 3. 事實檢查（程式） | 數字、比分、人名對不上 | 數字與比分整組比對、人名必須在事實清單、禁止詞（未判定的「爆冷」、季軍）、字數與數字預算 |
| 4. 編輯檢查（LLM-as-judge） | 邏輯、連貫、廢話 | 另一次模型呼叫逐條對照準則，不過就帶意見退回重寫，最多 2 次；仍不過就附編輯意見給人看 |
| 5. 人審＋回饋迴圈 | 前四道漏掉的 | Raymond 審稿 → claude.ai 寫成新準則與反例 → CLI 做成測試 → 同一種錯只需要講一次 |

推測句（資料庫外的背景）允許寫，但必須標「⚠️推測」並附待查清單，不能寫成確定語氣。

## 二、案例紀錄

格式：日期｜症狀（原文）｜怎麼發現｜根因｜解法｜驗證

### A. 捏造與數字錯誤

**A1 捏造團體賽比分**（09-30）
- 症狀：今日重點寫「男團決賽印尼 3–2 中國、女團決賽中國 3–0 日本」，資料裡根本沒有團體賽；還把「等一下，我寫錯了」的自我更正一起輸出。
- 發現：CLI 第一次實測 LLM。
- 根因：模型在素材不足時「補完」常見敘事；事實檢查把 3–2 拆成 3 和 2 分別比對，兩個數字各自在資料裡出現過就放行。
- 解法：比分改成**整組比對**（正反順序皆可）；拒收多段落或含「等一下／更正／我寫錯」的輸出；提示詞「摘要沒有的賽事不提」。
- 驗證：那次的真實錯誤輸出做成回歸測試（fe8b045）。

**A2 日期被當成比分，讓模型自算的數字混過去**（10-01）
- 症狀：模型寫「低 26 名」（自己算的），事實檢查沒擋。
- 根因：比分正規式把日期「2026-10-01」讀成 26-10、10-01，剛好湊出 26。
- 解法：比分前後不能接數字或連字號；數字比對忽略前導零。三種輸出共用同一檢查器，修一處三處受惠。

**A3 模型自己算新數字**（10-01）
- 症狀：「第 9 次碰面」「9-0」不在事實清單裡。
- 解法：提示詞禁止自算新數字；「X 勝 Y 負」允許寫成比分格式；事實清單直接提供常用的衍生數字。

**A4 比分角度寫反**（09-30）
- 症狀：「周天成以 21-10 21-11 不敵」，比分其實是對手角度。
- 解法：比分一律以句子主詞的角度書寫，事實清單同時給兩個角度。

### B. 邏輯與資訊量

**B1 數字沒交代場景**（10-01，R1）
- 症狀：「這 7 場裡最接近的一局，楊博軒／胡绫芳打到 19 比 21」，聽眾不知道是哪場。
- 根因：資料層只給了數字，沒給出處，模型寫不出來。
- 解法：紀錄型 facts 一律帶賽事年份、名稱、輪次、第幾局。

**B2 轉折沒有理由**（10-01，R2）
- 症狀：「轉折在 2024 丹麥公開賽 16 強，KIM Ga Eun 中途退賽。從那場起 WANG Zhi Yi 5 勝 1 負。」
- 根因：資料層只找出戰績翻轉點，沒有任何「為什麼」的素材。
- 解法：翻轉前後的排名、局分差、傷退次數、換搭檔一起給；找不到理由就禁止用「轉折」這類暗示因果的字。

**B3 段落跟主軸無關**（10-01，R3）
- 症狀：宿敵故事中間插「台灣這邊，周天成拿下男單 32 強……」。
- 根因：**是 claude.ai 寫交接單時留的例外**（賽果背景可以放台灣選手），模型照做。
- 解法：刪除例外；影片只講一個故事，台灣戰報移到粉專。
- 教訓：規則本身寫錯時，模型會忠實地放大錯誤。

**B4 廢話：必然成立的事**（10-01，R9）
- 症狀：「黃宥薰、劉廣珩／陳政寬、李佳馨／吳冠勳也都打進四強，對手全是後來的冠亞軍。」四強的對手本來就是冠亞軍。
- 根因：**提示詞自己寫了「列出輸給後來的冠亞軍」**。
- 解法：刪提示詞；資料層只在八強以前輸球時才產生「對手後來奪冠」的 fact；編輯檢查用「換成『當然』開頭仍成立就刪」判斷。

**B5 換角度重講同一個比分湊秒數**（10-01）
- 症狀：9/28 單一故事 32–46 秒把 21-11、21-14 從韓國角度再講一次。
- 解法：素材不夠就短（30–45 秒可），禁止重講同一比分。

### C. 敘事品質

**C1 只在報數據**（10-01，Raymond 兩次提醒；R5、R7、R10）
- 症狀：試寫腳本與粉專一段接一段「誰 幾比幾 贏誰」；claude.ai 自己寫的「三個雙打世界第一都沒拿金牌」初稿也一樣。
- 解法：一篇只挑 1–2 組主角（R10）；全篇數字 ≤ 5 個（R7，固定檢查）；粉專寫故事體、不拆條列（R5）；故事要有人物、處境、轉折、意義。
- 演進：「每段最多 1 個數字」原本固定檢查，成為退回主因，10-02 改成交給編輯判斷。

**C2 第一行看不出是羽球**（10-01，R4）
- 症狀：「8 次交手、16 局全輸。但仔細看比分……」滑過的人不知道在講什麼。
- 解法：第一行至少要有「羽球或賽事名」＋「跟誰有關」。

**C3 語氣跟時間不合**（10-01，R6）
- 症狀：比賽兩天後還用「這次亞運八強，她們又……止步八強」的新聞語氣。
- 解法：比賽日 +1 天內用新聞語氣，之後改故事語氣（開頭【羽球故事】），程式把天數放進提示詞。

**C4 故事套路重複**（10-01，未解）
- 症狀：亞運 5 天有 3 支是「前 X 場只贏 Y 場，現在連贏 Z 場」。
- 狀態：待處理（候選：同類型故事一週最多 2 次）。

**C5 沒發揮我們的優勢**（10-01，R11）
- 解法：素材固定分三區：【歷史】（必備）、【新聞】（有就要用）、【冷知識】（相關才用）；判斷法：拿掉當天比分後還剩有內容的段落。

**C6 技術上沒錯、但說法外行**（10-02，claude.ai 測試腳本）
- 症狀：「拆夥後，組合的積分也就一點一點歸零」。
- 發現：Raymond：「重組後就是積分歸零啊」。
- 事實：舊組合的積分確實是 52 週內逐站到期，但觀眾在意的是「雙打排名跟著組合算，重組就等於從零開始」。「一點一點」把重點放在不重要的過程上，內行人聽起來很怪。
- 解法：規則類敘述要用選手的說法講結論，不描述計算過程；審稿準則加反例。

### D. 資料誤讀（看起來對，其實錯）

**D1 沒查生涯就說「沒人注意」**（10-01，R8）
- 症狀：claude.ai 把亞運男雙冠軍 CARNANDO／MARTHIN 寫成「賽前幾乎沒人注意的組合」。
- 發現：Raymond（前男雙國手）一眼看出不對。
- 事實：生涯最高世界第 9，拿過多座 Super 500 冠軍。
- 解法：寫名氣判斷前必看生涯最高排名、冠軍、搭檔史。

**D2 把拆夥誤讀成低潮**（10-02，R12）
- 症狀：試推稿「排名一度滑到四十多名，這是一段重返的故事」。
- 發現：Raymond 質疑 → claude.ai 查資料庫。
- 事實：2024-08 拆夥（CARNANDO＋Bagas MAULANA、MARTHIN＋Shohibul FIKRI），2026-05-12 重組（重組時已不在排名表上，第 157 是拿下泰國公開賽冠軍後那週的排名，見 D4）；重組後第一站泰國公開賽就奪冠。
- 根因：雙打排名算「組合」，拆開期間積分歸零；資料層沒有搭檔史。
- 解法：career facts 加搭檔史、拆夥與重組日期；新增 `reunion`／`split` 故事類型。
- 教訓：看起來合理的推論（排名掉＝打不好）最危險，需要領域知識的人審。

**D4 把「奪冠後的排名」當成「重組時的排名」**（10-02，claude.ai 測試腳本）
- 症狀：腳本寫「重新組隊時，排名只剩第一百五十七」。
- 發現：Raymond 問「這段要怎麼查證」→ claude.ai 逐句查資料庫。
- 事實：兩人最後一次同場是 2024-06 印尼公開賽；組合排名一路掉到 2025-04 的第 80，之後就不在排名表上。第 157（2026-05-19，9,200 分、1 站）是泰國公開賽冠軍積分進帳後的第一週排名，所以重組時其實是「沒有排名」。
- 根因：只看排名快照的第一筆就當成起點，沒有對照那週有沒有比賽入帳。
- 解法：事實清單的排名一律附「發布日期＋當時累計站數」；「重組時／賽前排名」要取該站開賽前最後一次發布，沒有就寫「無排名」。
- 附帶發現：重組後還拿了 2026 台北公開賽冠軍，可以當故事素材。

**D5 事實檢查只核對「數字有沒有出現」，沒核對「意思對不對」**（10-02）
- 症狀：D4 的 157 有在事實清單裡，所以程式化事實檢查放行；錯的是「這個數字代表什麼時間點」。
- 發現：要 Raymond 自己問「怎麼查證」才被發現——agent 應該先自己查。
- 解法：見 notes 10-02 11:25（逐句引用事實＋獨立查證）。

**D3 估算排名被當成事實**（09-30 到 10-01）
- 症狀：2019 年以前官方排名 API 回 500，只能用自己重建的估算排名。
- 解法：日報標「（估算）」；腳本與粉專只用官方排名，估算值不進事實清單。

### E. 名稱與用語

**E1 外國選手譯名不一致、照抄未確認的譯名**（10-01）
- 症狀：同一人出現「坤拉武特／昆拉武特」「法罕／法漢」；寫手照抄範例裡 claude.ai 暫用的譯名。
- 解法：譯名只取台灣媒體原文「中文（英文）」、≥ 2 個來源才確認；範例載入時把未確認譯名換回英文；同一人只能一種寫法。

**E2 台灣選手沒有中文名**（10-01）
- 症狀：粉專把梁庭瑜寫成 LIANG Ting Yu。
- 解法：用中華羽協歷年甲組名單拼音比對（距離 0 且唯一才自動採用 182 位，其餘 184 位列人工確認）；比對不到就在備註請 Raymond 提供。

**E3 名次用語**（10-01）
- 演進：先定「巡迴賽不說獎牌」並加檢查 → Raymond 改成「金銀銅都可用、不用季軍／第三名」→ 移除舊檢查。
- 教訓：用語規則是編輯偏好，要能隨時改，所以集中在準則檔。

### F. 成本與穩定（生成相關）

**F1 推理強度太高：貴又會截斷**（10-01）
- 症狀：一天花 US$3.48；Opus high 每次輸出 5,000–6,000 token（腳本本身約 1,000），還會把 JSON 截斷。
- 解法：同一批素材做 high／medium／low × Opus／Sonnet 對照實驗：Opus low 兩個故事都一次通過、每支約 US$0.05；Sonnet 便宜但常超字數、自算數字。寫作定為 Opus low、每日預算 US$1。
- 後續：10-01 晚 Raymond 判定 Sonnet 寫得不好，寫作全改 Opus；10-02 編輯也改 Opus。

**F2 測試誤呼叫真的 API**（10-01）
- 症狀：開關改成 dry 後，測試走到腳本產生、真的花錢。
- 解法：`tests/conftest.py` 讓所有測試看不到開關與 webhook。

## 三、面試可以怎麼講（草稿，之後再修）

**一句話**：我做了一個每天自動寫羽球短影音腳本與粉專貼文的 agent。最大的困難不是讓 AI 寫出來，而是讓它寫得**對**而且**像人寫的**。

**STAR 版本**
- 情境：AI 會捏造比分（寫出不存在的團體賽結果）、說廢話（「四強輸給冠亞軍」）、還會把看似合理但錯誤的推論寫成事實（把拆夥誤讀成低潮）。
- 任務：在不犧牲成本的前提下，讓錯誤率趨近 0，並讓內容有故事性。
- 行動：建了五道防線——資料層只給可驗證事實、準則檔集中管理、程式化事實檢查、LLM 編輯檢查、人審回饋迴圈；每個被抓到的錯誤都變成一條準則＋一個回歸測試；用對照實驗選模型與推理強度。
- 結果：同一種錯只需要指出一次；每支腳本成本約 US$0.05；累積 12 條有反例的審稿準則（R1–R12）。

**可以延伸的重點**
- 為什麼「給 LLM 事實清單」比「給原始資料」好（B1、B4）。
- 為什麼規則寫錯時模型會放大錯誤（B3、B4）——prompt 也是需要 code review 的程式。
- 為什麼需要領域專家在迴圈裡（D1、D2：我是前國手，才看得出拆夥那件事）。
- 成本與品質的取捨是用實驗決定的，不是憑感覺（F1）。
